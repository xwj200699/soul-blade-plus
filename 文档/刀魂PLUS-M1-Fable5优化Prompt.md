# 四、P0：修复单文件资源加载

## 4.1 已确认的打包问题

当前 HTML 已经内嵌约 30 张 `assets/ui-lab/*.png` 素材，包括标题背景、角色大头像、HUD、VS 徽章、场景原画和胜负结算界面。

但 `_loadImg()` 运行时会请求：

```text
/assets/ui-lab/*.webp
```

内嵌资源表中的实际键名却是：

```text
assets/ui-lab/*.png
```

存在两个问题：

1. 请求路径多了开头的 `/`；
2. 请求格式从 `.png` 被改成了 `.webp`。

因此高质量 UI 素材无法命中 `window.ASSETS_B64`，只能触发程序化 fallback。当前至少 24 个直接 UI 请求会发生这种失配，约 16.84 MiB 的 UI 图片虽然已被打包，却没有在实际界面中生效。

## 4.2 必须完成的修复

单文件版本的 `_loadImg()` 应优先读取真实存在的内嵌 PNG：

```js
i.src = 'assets/ui-lab/' + file;
```

同时增强单文件资源解析逻辑：

- 去除路径开头的 `/`；
- 能从完整 URL 中提取 `assets/...`；
- 清理查询参数和哈希；
- 当 `.webp` 不存在时自动查找同名 `.png`；
- 不允许向不存在的外部目录发送请求；
- 所有 UI 图片必须从 `window.ASSETS_B64` 成功加载；
- 资源失败时仍可显示错误信息，但正式验收中不得触发 fallback。

建议实现统一的资源解析函数：

```js
function resolveEmbeddedAsset(input) {
  let key = String(input).split('?')[0].split('#')[0];

  try {
    key = new URL(key, location.href).pathname;
  } catch (e) {}

  const assetIndex = key.lastIndexOf('/assets/');
  if (assetIndex >= 0) key = key.slice(assetIndex + 1);

  key = key.replace(/^\/+/, '');

  return (
    window.ASSETS_B64[key] ||
    window.ASSETS_B64[key.replace(/\.webp$/i, '.png')] ||
    null
  );
}
```

可以根据现有代码结构调整，但必须解决实际映射问题，不要只增加注释。

## 4.3 清理无效资源

完成修复后，审计所有内嵌素材：

- 重复素材删除；

# 八、P1：重做公平 AI

当前困难 AI 使用：

```js
cheatRead: true
readP: 0.92
```

这相当于直接读取玩家输入。必须移除这套机制。

AI 只能根据已经发生或已经进入可见前摇的游戏状态做决策，包括：

- 双方距离；
- 当前动作；
- 攻击前摇和收招；
- 是否处于空中；
- 投射物位置；
- 血量；
- 能量；
- 版边位置。

## 8.1 EASY

- 反应延迟 24–40 帧；
- 很少防御；
- 很少使用完整连段；
- 不稳定使用超必杀。

## 8.2 NORMAL

- 反应延迟 12–20 帧；
- 能进行基础防御和惩罚；
- 偶尔使用完整连段；
- 能合理使用必杀与超必杀。

## 8.3 HARD

- 反应延迟 5–9 帧；
- 能识别明显前摇和收招；
- 能进行版边压制、起身压制和连段；
- 允许犯错，不能读取玩家当前帧输入；
- 不允许获得额外能量或隐藏属性。

困难应该表现为“理解系统且执行稳定”，而不是“知道玩家刚刚按了什么”。

# 十五、最终执行判断

本轮不是追求“功能数量更多”，而是完成以下收敛：

1. 已经打包的素材真正生效；
2. 六名角色达到同一视觉质量；
3. 三名新增角色具备独立战斗身份；
4. 单人、双人、训练三个核心模式真实可玩；
5. AI 强度来自合理判断，而不是读取玩家输入；
6. 最终文件经过实际运行和完整流程验证。

在这六项完成之前，不要新增角色、场景、剧情或成长系统。否则下一版可能功能更多，但第一眼仍然是素材拼接 Demo。
